# WorkBuddy Local 完整执行规划与验收蓝图

状态：实施与验收中。本文件依据 2026-10-20 对真实 VM、源码和面板的检查持续更新。执行限定在 VM 与本地工作区，不修改生产环境。

## 目标和约束

把 WorkBuddy Local 做成低噪声、前后端契约明确、资源按需工作的本机工作台。界面采用 Claude 风格的克制排版，保留玻璃材质、账号圆环和液态动效作为视觉焦点。

- 每个前端操作必须有真实后端接口、加载/错误状态和成功回读。
- 未登录不请求账号数据，不刷新余额。
- 登录后同步全部账号余额和状态；不刷新订阅，不测节点延迟。
- 启动动画约 8 秒目标、10 秒硬上限，最终按实测耗时调整；超时直接进入工作台，后台继续同步。
- 订阅和节点使用缓存，只有用户手动刷新/测试时才访问上游。
- 错误记录仅保留模型调用错误，最长 24 小时并限制数量和容量。
- 不把 DeepSeek-V4.1 Flash max 冒充为可用模型。当前可用的最高 DeepSeek 智能体档位是 V4 Pro / ultra。
- 用户明确要求：Meta 内核和反代内核是第三方创作，本项目维护者不熟悉，禁止修改内核实现源码。`internal/metacore`、`third_party/meta` 及内核相关 vendor 实现作为只读边界；功能优先通过 WorkBuddy 面板 API、业务编排、前端和配置层实现。若需求确实无法在边界外完成，先停下并说明具体阻塞点，不得自行扩大修改范围。

## VM 基线和根因

2026-10-20 只读扫描：Ubuntu amd64，4 vCPU，7.8 GiB RAM，可用约 7.1 GiB，无 Swap；38 GiB 磁盘已用约 2.7 GiB；16 个账号文件；WorkBuddy 目录约 81 MiB。

Windows 的 127.0.0.1:7863 已映射到 VM 192.168.189.128:7863，但 VM 没有 WorkBuddy/Mihomo 监听端口。workbuddy.service 自动重启约 445 次，错误为 200/CHDIR，因其工作目录 /opt/workbuddy 不存在。workbuddy-mihomo.service 错误为 203/EXEC，因其二进制 /opt/mihomo/mihomo 不存在。真实文件在 /opt/workbuddy-local，包括 wb2api、Linux amd64 Mihomo、配置、数据和账号。gateway.service 是独立 DeepSeek Gateway，本计划不修改它。

根因是 systemd、应用二进制和内核路径来自两套不同部署布局。扫描还发现应用目录配置监听 0.0.0.0:7863、使用相对账号和数据路径，而 /etc/workbuddy-local/config.json 虽监听回环，仍使用相对路径。当前首先要统一为单一目录、绝对配置和数据路径及受管内核生命周期，而非先做 UI。

## 目标运行架构

~~~text
浏览器 127.0.0.1:7864
  -> Windows 宿主机 SSH 本地隧道
  -> VM 127.0.0.1:7863
  -> WorkBuddy Go 面板，只监听回环
       -> 账号池、上游、任务、错误记录
       -> metacore.Manager 管理的 Mihomo 子进程，只监听回环控制器/账号入口
~~~

统一发行根目录为 /opt/workbuddy-local。当前 VM 的 /var/lib/workbuddy-local 为空，阶段 1 先使用现有账号和 data 路径并显式配置绝对路径，避免迁移成空池；后续迁移必须覆盖 state_file 同目录派生的 password、usage、conversations、model-policy、bindings、meta/providers、spool、request-logs，并逐项比较数量与哈希。Mihomo 由 WorkBuddy 的 metacore.Manager 作为受管子进程启动、健康检查、空闲退出和回收。systemd 只管理一个 WorkBuddy 主服务。

## 启动、登录和同步

无有效 Cookie 时：加载静态壳、字体和动画，播放英文 AI 名称并自然显现密码输入。密码成功后：设置会话 Cookie，启动一次全账号余额/状态同步，动画继续播放；同步完成或到达 10 秒硬上限时进入工作台。有有效 Cookie 时跳过密码输入，进入同步阶段。跨设备需要重新登录。

英文名称包括 GPT、Claude、Gemini、DeepSeek、Qwen、Kimi、GLM；不显示进度百分比和冗余技术说明。未登录阶段不暴露账号明细。

同步约束：

- 后端实现单飞任务；多标签页复用一轮同步，不重复请求。
- 账号并发使用 2-3 个工作槽，尊重上游超时和已有资源限制。
- 账号结果增量持久化；响应体及时关闭。
- 不刷新订阅、不测节点、不做无关模型探测。
- 超时不弹失败窗，进入系统后显示缓存时间和真实账号状态。
- 页面刷新只刷新余额、冷却、凭据有效性和账号状态。

接口建议：会话 bootstrap 的 POST 用来复用/创建任务，GET status 返回 running/completed/partial 和计数；现有 POST balance_all 保留手动刷新，但确认只作用于账号数据。登录使用 HttpOnly、SameSite、24 小时绝对有效期 Cookie；退出、改密和服务端撤销后失效。未登录不能触发账号刷新。

四种启动动画以本地受控模块提供统一 start、setPhase、finish、destroy 生命周期。系统设置支持选择、预览和恢复默认。检查其定时器/监听释放、手机布局、减少动画、超时销毁以及不加载任意外部脚本。

## 账号出口、订阅和节点

Meta 先集成到账号出口页，不立即增加主导航。页面顺序：账号节点绑定、订阅管理入口、节点列表。若实际内容放不下，再评估单独导航。

订阅可有 3、4 或更多条，不设“两条”产品限制；当前 metacore 硬上限为 16 provider、1000 节点、64 MiB provider 数据、256 个账号绑定，超过时返回明确 4xx。顶部小入口只显示订阅数和启用数；点击弹窗列出名称、启用状态、节点数量、更新时间、手动刷新、启停、删除和脱敏 URL。完整 HTTPS 地址仅由用户主动查看/复制。订阅 URL 不写日志、不在普通响应中回显。删除有绑定的订阅时返回冲突或明确迁移，不能静默直连。

订阅 API 建议为列表、添加、PATCH 启停/名称、按 ID 刷新、按 ID 删除和诊断。诊断显示 HTTP 状态、Content-Type、响应类型识别、解析节点数和失败原因，不返回敏感响应正文。

节点来源切换提供全部和每条订阅。排序在合并绑定状态后执行：当前账号已绑定节点优先，可用节点按延迟升序，未检测/失败靠后，再以稳定 node id 打破并列；分页在排序后进行。provider 需持久化订阅名称，使同名节点可显示“订阅名 · 节点名”。桌面使用连续行或两列，手机单列，数据顺序固定。账号每次只绑定一个节点，不同账号可绑定不同节点。绑定流程必须更新 Mihomo、持久化账号代理、回读 binding；失败保留旧绑定，不退回直连。打开页面或弹窗只读缓存，只有明确点击“开始测试”才触发延迟测试。

## 前后端契约和 JSON

每个 UI 控件登记 HTTP 方法/路径、请求字段、响应、错误码、加载/超时、回读接口和权限/CSRF。后端 handler、持久化与敏感信息过滤先完成，再接前端；成功以服务端回读为准。

账号 JSON 增加独立适配层，覆盖根对象/数组、嵌套 auth/account、驼峰/下划线字段、代理、realm、device_token、token 和秒/毫秒过期时间。先分析真实文件 schema，再以脱敏 fixture 验证。导入预检逐项返回 index、UID、字段、错误码和说明；检查 UID、token、realm、代理 URL 和大小；整批通过后原子写入。明确已存在账号是替换凭证同时保留健康状态/代理，还是完整替换。不能将 OAuth、签到或余额请求隐式附加在文件导入流程中。真实 token 不复制到计划或测试日志。

## 视觉与页面规划

采用深石墨/深蓝黑底、玻璃层、柔和边界、少量强调色和明显留白；不复制蓝色大屏或金融模板，不把每项数据拆成相同卡片。减去英文眉标题、编号、重复解释、小字和多余箭头。主要信息由排版、间距和位置表达，次要字段进弹窗/抽屉。

概览采用非对称 2/3 + 1/3：左侧账号圆环和统计，右侧昼夜组件及简约 API 组件。圆环旋转渐出，统计数字慢慢展开；状态为总数、可用、冷却、禁用并复用账号池颜色。昼夜切换参考 Uiverse，点击中心扩散，支持键盘和减少动画。API 框只显示 Base URL 和复制，其他地址放详情。

导航名称：概览、账号池、账号任务、账号出口、积分用量、积分构成、模型查看、错误记录、系统设置。当前导航只显示左侧短色条和文字强调，不做整行大面积背景。全屏导航靠近视口侧边；手机使用紧凑顶栏或安全区底栏。

账号池只显示决定操作所需信息。账号节点选择区桌面约占行宽 1/3，手机改两行。

账号任务显示步骤汇总和成功/失败/跳过数字，不铺全部账号；点击失败数字打开按需加载的详情面板，失败进度用红色。

积分构成不显示 remain <= 0 的包，完整数字显示如 12500/12,500；未知余额不作为零。余额保护阈值保留后端固定值 100，前端不展示配置表单。

模型查看页简化为名称、标识、能力、上下文和状态。移除容易误导的“上下文展示”操作，必要时以只读详情替代。

错误记录作为独立导航。列表只显示时间、类别、模型；点击弹窗按 ID 加载账号、请求 ID、截断且脱敏的上游错误和状态。当前 telemetry.Event 缺少错误正文/类别，reqlog 默认保留 7 天且无 OnlyErrors；需新增字段与详情接口。阶段 2 先给同步/错误事件设置硬条数和字节上限，阶段 7 完成 OnlyErrors、24 小时 TTL、MaxRecords、MaxEntryBytes。只存 401、402、403、408、409、429、5xx 等模型错误，不存成功请求正文。

系统设置标题为“系统设置”。移除旧主题和积分阈值控件；保留动画选择、管理密码、服务/内核状态和简约 API 信息。模块纵向错落排布，不强制全部横向等宽。

字体使用远程字体加本地回退：英文选择 Source Sans 3、Instrument Sans、DM Sans 或 Manrope 中许可和稳定性合适者；中文用 Noto Sans SC/思源黑体；少数大标题可选 Source Serif 4/Noto Serif SC。当前 CSP 未开放 font-src，实施前要只允许固定字体源并明确第三方连接元数据，或将字体静态打包；使用 font-display: swap 和本地回退，字体不可达不阻塞首屏。

液态玻璃和底部流动主要是客户端 GPU 工作，不会持续增加 VM CPU。控制 backdrop-filter 面积和图层；只用 transform/opacity；页面隐藏时暂停，手机降模糊，减少动画时关闭，不遮挡交互和滚动。

## 内存与生命周期

常驻仅保留账号摘要、当前绑定、会话、最近余额快照和功能状态。进入页面才加载积分包、模型详情、订阅/节点、错误记录、任务详情。用户主动触发余额刷新、订阅刷新、节点检测和失败详情。

单飞账号同步、2-3 并发；节点检测无轮询；订阅默认缓存；页面离开释放轮询、监听和临时状态；节点历史限制条数；订阅原文落盘、内存只留摘要；HTTP body 有大小限制并及时关闭；维持单 Mihomo 内核多账号入口。以现有 GOMEMLIMIT 384MiB、并发 2、内存缓存 32MiB/128 entries 为基线，使用 RSS、启动时间和并发测试测量后再调。VM 无 Swap，若验证出现 OOM 再另案讨论，不顺带改系统资源。

错误记录同时设置 24 小时 TTL、最大条数、单条上限和总容量；不把全部详情常驻内存。

## 分阶段实施

### 阶段 0：基线与备份
记录 VM、映射、版本、systemd、配置/数据目录、端口和安全边界；建立 state_file 派生文件清单并核对 auths 文件数/哈希。记录 Gateway unit、监听地址/端口、数据目录和关键文件哈希作为不变基线。把工作区内含凭据的临时 JSON、Mihomo secret 和探针输出收容到受限目录或加密备份，后续轮换默认管理密码与 secret。完整备份现有 WorkBuddy 数据。不得进行未审查的递归删除。

通过条件：备份存在且可读；真实凭据不会进入源码、日志或测试样例。

### 阶段 1：修复 VM 部署链路
统一路径为 /opt/workbuddy-local，核对 wb2api、内核哈希、架构、配置、数据和服务用户；移除旧独立 Mihomo unit 的启用/自动重启配置，使用项目提供的单一 workbuddy-local.service，由 Manager 管理 Mihomo 子进程；服务使用绝对路径、非 root、健康检查及有界重启。迁移状态先备份并演练，不清理 Gateway。

通过条件：systemd-analyze verify 通过；一个 WorkBuddy 服务稳定运行并能按需管理单个 Mihomo；7863 回环健康接口返回成功；浏览器通过 SSH 隧道访问；重启计数不再增长；Gateway unit、监听端口、数据目录和关键哈希与阶段 0 基线一致。

### 阶段 2：启动会话与账号同步契约
实现 24 小时 Cookie、bootstrap 单飞、登录后全账号余额/状态同步、部分完成和超时状态。明确页面刷新只刷新账号。

通过条件：未登录请求不触发余额；多标签复用一次；账号并发有上限；超时后进入工作台；余额结果持久化和回读正确；Go 测试通过。

### 阶段 3：账号 JSON 兼容
对真实文件字段结构做脱敏 schema 分析，建立预检/导入适配器和回归 fixture。

通过条件：原文件结构无需手改即可导入；坏字段、重复 UID、坏代理和大文件正确拒绝；不泄露 token；已有账号状态规则符合预期。

### 阶段 4：多订阅、节点与绑定
订阅持久化和多订阅管理；产品不设两条限制，但受当前 16 provider、1000 节点、64 MiB provider 存储和 256 binding 硬上限约束，超限返回明确 4xx；诊断/刷新/启停/删除；节点来源选择和稳定排序；账号单节点绑定与回读；删除绑定节点保护。功能限制在面板管理 API 和 UI；凡必须修改内核实现才能完成的行为，列为需用户单独确认的设计决策。

通过条件：至少四条模拟订阅同时管理；同名节点不冲突；绑定失败保留旧状态；启动与页面读取不触发测速；节点测试仅手动执行。

### 阶段 5：页面结构和信息层级
实现概览、账号池、账号任务、账号出口、积分用量/构成、模型查看、错误记录和系统设置的整体重排；旧主题入口、阈值表单、独立节点测试卡和无关文案删除；刷新按钮采用边框高亮。

通过条件：桌面信息层级清楚、手机无横向溢出；所有按钮都有后端契约；失败结果按需展开；积分逻辑正确；页面不再像普通中转站控制台。

### 阶段 6：动画、字体和材质
制作四个本地动画模块、选择/预览设置、英文 AI 名称、密码过渡、登录同步阶段、超时结束、远程字体回退、圆环旋转渐出、数字展开、主题扩散和底部流动。

通过条件：所有动画可 destroy；字体不可用仍可登录；减少动画直接切换；超时后不再阻塞；动画无布局跳动和无界 GPU/CPU 工作。

### 阶段 7：错误记录、内存和清理
实现错误类别记录、24 小时 TTL 和上限；详情按需加载；停止无用轮询；释放 body、计时器和事件；测量 RSS 和账号刷新性能。

通过条件：日志不超限；页面往返不累积定时器；节点无自动探测；同步/任务并发下内存可解释且不无界增长。

### 阶段 8：完整回归和部署验收
运行 Go、Node 测试；VM 服务健康、浏览器 E2E、宽屏/普通桌面/手机、键盘、双主题、减少动画、慢网、错误路径、资源测量和回滚演练。

通过条件：关键路径全部通过，所有失败项有明确归属；生产边界无写入；验收报告记录实际版本和数据。

## 验收矩阵

- 服务：非 root、固定内核、端口回环、依赖顺序、健康检查、SIGTERM、持久化恢复。
- 会话：24 小时 Cookie、未登录零账号请求、退出/改密撤销、跨设备重新登录。
- 同步：16 账号单飞、2-3 并发、超时、部分完成、手动刷新只更新账号。
- Meta：4+ 订阅、同名节点、手动刷新、启停、绑定冲突、错误回滚和状态回读。
- UI：4 种动画、英文名字、登录过渡、超时进入、概览圆环、失败详情、完整积分、错误弹窗和简约设置。
- 设备：桌面宽屏、1366 宽、390 宽；深浅主题；键盘；prefers-reduced-motion；字体网络失败。
- 资源：启动时长 P50/P95/max、账号同步耗时、峰值 RSS、错误记录容量、动画 FPS、无持续节点请求。

## 回滚和风险

每阶段保留源码、配置、服务单元和数据备份。迁移先演练后切换；面板层 Meta 变更失败回滚 provider/binding（不改 Meta 内核实现）；动画失败回退静态登录；字体失败回退本地；余额刷新失败保留旧快照；不执行 destructive reset、不清理未经确认的数据。

主要风险：配置与账号数据路径错配、多个标签重复同步、Meta 删除时丢绑定、前端成功但后端未持久化、远程字体阻塞、动画 timer 泄漏、错误日志超量、移动端玻璃模糊耗电。

## 已冻结的默认决策

登录触发全部账号余额同步，并由 2-3 槽信号量和单飞任务约束；8 秒目标/10 秒硬上限；模型倍率预热不能阻塞 HTTP 监听或登录动画预算；启动不刷新订阅或节点；节点检测按需且打开页面不自动 POST 测试；订阅集成账号出口并受 16 provider 等硬上限；每账号一个节点；手动页面刷新只刷新账号；Cookie 当前浏览器 24 小时（当前源码 12 小时，阶段 2 必须修改并明确 SameSite 与 VM 重启语义；当前会话在内存中，重启会失效）；错误记录独立导航并保留 24 小时；Meta 是否拆导航待阶段 4 的真实页面容量评估；英文人文无衬线、中文现代无衬线，少量大标题可用衬线；积分保护值固定后端 100。

每个阶段开始前先冻结接口契约和测试；阶段验收通过后再推进下一阶段。若扫描发现与本文不符，先更新规划和验收表再实施。
